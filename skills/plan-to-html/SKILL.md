# Plan to HTML

会話、作業計画、Markdown、JSONなどに含まれる Plan を、ブラウザでそのまま開ける単一の HTML ファイルに変換する。情報の意味と状態を保ち、見出し・進捗・マイルストーン・依存関係・リスク・検証項目を読みやすく整理する。

## 入力の扱い

- 会話中の Plan、ユーザーが指定したファイル、または明示された Markdown・JSON を入力として使う。
- Plan の目的、スコープ、成果物、タスク、状態、依存関係、リスク、意思決定、検証項目、未解決事項を抽出する。
- 明示されていない担当者、期限、進捗率、完了状態、依存関係を推測して追加しない。情報が不足する場合は項目を省略するか「未定」「要確認」と表示する。
- 状態は `完了`、`進行中`、`ブロック`、`未着手`、`要確認` に正規化する。元の状態が曖昧な場合は `要確認` とする。
- 明示された進捗率だけを進捗バーに反映する。進捗率がない場合は数値を作らず、状態ラベルだけを表示する。

## HTML の出力

1. ユーザー指定の保存先を優先する。指定がなければ、作業対象プロジェクトのルートに `plan.html` として保存する。既存ファイルを上書きする場合は、ユーザーが上書きを明示しているか確認する。
2. `<!doctype html>`、`lang="ja"`、`meta charset="utf-8"`、viewport を含む完全な HTML 文書を作る。
3. CSS と必要最小限の JavaScript は HTML 内に埋め込み、CDN、外部 CSS、外部フォント、外部画像、ビルド手順に依存させない。
4. Plan の本文を HTML に挿入するときは、`&`、`<`、`>`、`"`、`'` をエスケープする。入力内容を JavaScript コードとして実行しない。
5. 次の順序を基本構成とする。情報がないセクションは作らない。

   - `header`: Plan のタイトル、目的の短い要約、全体状態、生成日
   - `main`: 概要、スコープまたは成果物、マイルストーンとタスク、依存関係、リスク、検証項目、未解決事項
   - `footer`: 入力元または生成時点（明示できる場合のみ）

6. 見出しには `h1`〜`h3`、リストには `ul`／`ol`、状態には `span` などの意味のある要素を使う。マイルストーンは順序がある場合 `ol`、依存関係やリスクは `ul` または表で表現する。
7. `details`／`summary`、`progress`、リンク付き目次などのネイティブ要素は、情報量が多い場合に限って使う。JavaScript でしか操作できない UI を必須にしない。

## デザイン基準

- 白または淡い中立色の背景、濃い本文色、1px の境界線、控えめな角丸を基本にする。強いグラデーション、過度な影、装飾目的の画像は使わない。
- 画面幅に応じて 1 カラムから 2 カラムへ変化するレスポンシブレイアウトにする。本文の最大幅を設け、長い行を避ける。
- 状態は色だけでなく、テキストラベル、アイコン相当の記号、または `aria-label` でも識別できるようにする。色覚差を考慮し、十分なコントラストを確保する。
- `@media print` を追加し、背景色や操作用 UI に依存せず印刷できるようにする。リンク先が重要な場合は印刷時にも URL が分かるようにする。
- 外部ネットワークがなくても内容を読めることを優先する。絵文字や特殊記号は意味を損なわない範囲で使用する。

## 検証

- 保存したファイルが存在し、HTML の開始・終了タグと未置換のプレースホルダーがないことを確認する。
- 可能ならブラウザまたは HTML プレビューで開き、タイトル、長いタスク名、状態表示、狭い画面幅、印刷レイアウトを確認する。
- 内容が入力 Plan と一致しているか、特に状態・期限・担当者・数値を再確認する。
- 検証できない項目は成功したと断言せず、完了報告に制限事項として記載する。

## 完了報告

HTML ファイルへのリンク、含めた主なセクション、実施した検証、残っている制限事項を簡潔に報告する。HTML 本文をチャットに大量に貼らず、必要な場合だけ短い抜粋を示す。
