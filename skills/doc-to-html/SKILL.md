# Doc to HTML

仕様書、実装計画、技術提案、不具合調査、調査レポートなどの文書を、ブラウザで直接閲覧・操作できる**単一の自己完結型 HTML ドキュメント**として生成・変換する。

単なるテキストのHTML化ではなく、**「左にメインコンテンツ（本文・モック・図解）」「右にスクロール追従する目次」を配置したシンプルで洗練されたドキュメント**を作成する。

---

## 適用ユースケースと埋め込み要素

| ドキュメント種別 | 本文（テキスト説明） | 文書内に埋め込むインタラクティブ要素 |
| :--- | :--- | :--- |
| **仕様書・要件定義 (PRD)** | 背景、ユーザーストーリー、機能要件、エッジケース | **インラインUIモック**（幅切替・状態切替・タブ・モーダル・フォーム） |
| **実装計画・ロードマップ** | スコープ、フェーズ定義、タスク一覧、リスク・前提 | **フェーズ展開アコーディオン、タスク連動進捗バー** |
| **技術提案・アーキテクチャ** | 選定理由、メリット・デメリット、システム構成 | **案A / 案Bの比較トグル**、CSS/SVGによるデータフロー図 |
| **不具合調査・改善案** | 原因分析、再現手順、修正方針 | **現状（Bug）と修正後（Fix）の挙動シミュレーション** |
| **API・データモデル設計** | エンドポイント一覧、パラメータ定義、型定義 | **リクエスト / レスポンスのインタラクティブプレビュー** |
| **技術リサーチ・アルゴリズム** | 理論解説、ベンチマーク結果、まとめ | **パラメータ調整で変化する簡易シミュレータ / グラフ** |

---

## レイアウト構造（左: コンテンツ / 右: 目次）

デスクトップ時は**左側にメインコンテンツ、右側に追従する目次（On this page）** を配置する 2 カラム構成とする。

```text
+-------------------------------------------------------------------------------+
|  Header: タイトル、種別バッジ、メタ情報（日付・ステータス）、[📋 Markdownコピー]    |
+-------------------------------------------------------+-----------------------+
|  [メインコンテンツ (左側)]                             |  [目次 (右側)]         |
|  (max-width: 760px)                                   |  (position: sticky)   |
|                                                       |                       |
|  1. 概要・背景                                         |  目次                 |
|     読みやすい段落テキスト...                          |  - 概要・背景         |
|                                                       |  - UI設計案           |
|  2. UI設計案                                           |  - 画面遷移・フロー   |
|     +-----------------------------------------------+ |  - 実装手順           |
|     | [📱 Mobile | 💻 Desktop]  [Normal | Error]    | |                       |
|     | --------------------------------------------- | |                       |
|     | 触れるインラインUIモック                      | |                       |
|     +-----------------------------------------------+ |                       |
|                                                       |                       |
|  3. 画面遷移・フロー                                   |                       |
|     動的なステップ進行ダイアグラム...                 |                       |
+-------------------------------------------------------+-----------------------+
```

### レイアウト仕様
- **全体コンテナ**: `max-width: 1080px` 程度で中央配置。
- **左側（メインコンテンツ）**: `flex: 1; max-width: 760px;`。文章とモック・図解を読みやすく縦に並べる。
- **右側（目次 / Table of Contents）**: `width: 220px; position: sticky; top: 2rem;`。見出しへのスムーズスクロールリンク。
- **レスポンシブ（モバイル対応）**: 画面幅が狭い場合は 1 カラムに自動折りたたみ（目次は冒頭に配置または非表示）。

## デザイン原則（Paper & Solid, Warm Cream Tone）

HTMLの `<style>` には、以下の**CSSデザイントークン**をそのまま埋め込んで使用する。

```css
:root {
  /* Canvas & Paper */
  --bg: #f7f5f0;              /* 全体背景（淡いクリーム紙） */
  --paper: #ffffff;           /* カード・モック枠（純白） */
  --ink: #1f1e1d;             /* 本文テキスト（インクブラック） */
  --muted: #787571;           /* 目次・注釈・サブテキスト */
  
  /* Borders */
  --line: #e8e5de;            /* 通常の境界線 */
  --line-strong: #cbc5ba;     /* ホバー・アクティブ枠 */
  
  /* Accent & Info（上質なセピア・ウォームブラウン） */
  --accent: #695a42;
  --accent-soft: #f2efe9;
  
  /* Status Colors */
  --green: #376b4d;           /* 成功・推奨・Fix */
  --green-soft: #edf5ef;
  --amber: #8c5e1e;           /* 警告・要確認・進行中 */
  --amber-soft: #fbf5eb;
  --red: #99483f;             /* エラー・危険・Bug */
  --red-soft: #faf0ed;
  
  /* Code & Mono */
  --code: #292724;
  --code-bg: #f2efe9;
  
  /* Geometry - Sharp & Solid */
  --radius: 2px;              /* 角丸（0px〜2pxの直線基調） */
  --shadow: none;             /* 影は一切使わない */
  
  /* Typography */
  --font-sans: system-ui, -apple-system, BlinkMacSystemFont, "Segoe UI", Roboto, sans-serif;
  --font-mono: ui-monospace, SFMono-Regular, Menlo, Monaco, Consolas, monospace;
}
```

- **シャープな形状とノーシャドウ（No Shadows, Sharp Edges）**:
  - `border-radius` は `var(--radius)`（`2px` 以下）。直線的でソリッドな矩形。
  - `box-shadow: none`。紙とインクのように、1px のボーダーと淡い背景のコントラストだけで端正に構成する。
- **タイポグラフィ重視**:
  - 本文は `var(--font-sans)`、コードは `var(--font-mono)`。
  - ゆとりのある行間（`line-height: 1.75`）と文字間（`letter-spacing: -0.01em`）で上質な読み心地を作る。

## インタラクティブ要素の実装基準

### 1. インラインUIモック
- UI提案のセクションでは、テキストの直下に**触れるモックカード**を配置する。
- **デバイス幅切り替え**: モック上部に `📱 Mobile (375px)` ⇄ `💻 Desktop` の切り替えボタンを設置。
- **UIステート切り替え**: `[Normal]` / `[Empty]` / `[Loading]` / `[Error]` などの状態タブを設置し、エッジケースのUIをその場で確認可能にする。
- **軽量操作**: ボタンクリック、タブ切り替え、モーダル開閉、フォーム入力をインラインの Vanilla JS で実装する。

### 2. Markdown / AI指示用コピー機能
- ヘッダー右上にシンプルな `📋 Copy Markdown` ボタンを設置。
- ワンクリックで要約テキストをクリップボードにコピーし、次期プロンプトや GitHub Issue に貼れるようにする。

### 3. 比較ウィジェット (Comparison)
- 案A / 案B、Before / After をシンプルなセグメントボタンやトグルで切り替え可能にする。

### 4. 動的ダイアグラム / フロー図
- CSS Flexbox またはインライン `<svg>` でミニマルなフロー図を作成。クリックでステップが進む演出を入れると直感的。

## 文体・ライティング規律（AI構文・ポエムの排除）

- **エンジニアの実務トーン（事実・課題・決定ベース）**:
  - 「主戦場は〜」「〜の段階に入っている」「〜の土台となっている」「〜の進展を棚卸しし」といった評論家的なポエム・大げさな要約は一切書かない。
  - 「何ができていて、何が壊れていて、なぜそれが必要か」を事実ベースで端的に書く。
- **過剰な免責・前置き（Disclaimer）の禁止**:
  - 「これは設計確認用であり、実画面そのものではありません」「〜をもとに整理した」「未実装の提案」などの言い訳・注釈ノイズは書かない（見れば分かる）。
- **無駄な装飾キッカー・ナンバリングの禁止**:
  - `01 / summary` や `02 / shipped` のような装飾用キッカーは使わず、シンプルな見出し（`概要`, `直近の実装`, `次の課題`）にする。
- **生きた課題感の記述**:
  - 単なる機能の平坦な羅列（体言止め）ではなく、「現状の課題 → どう解決するか」を短く切れ味のある文章で書く。

## 技術制約と品質ルール

- **完全自己完結 (Zero Dependencies)**:
  - 外部 CSS / JS / CDN / Webフォント / 外部画像に一切依存しない。
  - 全てインラインの `<style>` と `<script>` で完結し、完全オフラインでも100%美しく動作すること。
- **レスポンシブ & 印刷対応**:
  - スマホからPCまで綺麗に表示され、`@media print` で印刷・PDF化しても崩れないこと。

## 生成手順と出力

1. **入力情報の分析**:
   - 会話ログやファイルから、目的・要件・技術仕様・UI案・フローを整理する。
2. **HTMLファイルの生成 & 命名規則**:
   - 完全な単一 HTML ファイル（`<!doctype html>` から `</html>` まで）を作成する。
   - ユーザーから保存先の指定がなければ、プロジェクト内の `docs/specs/` ディレクトリ配下（存在しない場合は作成）に、**日付プレフィックス付きのケバブケース**で保存する。
     - **命名形式**: `docs/specs/YYYY-MM-DD-<内容・トピック>.html`
     - **例**:
       - `docs/specs/2026-08-16-perform-position-overwrite-fix.html`
       - `docs/specs/2026-08-16-timeline-redesign-spec.html`
       - `docs/specs/2026-08-16-vector-rendering-proposal.html`
3. **完了報告**:
   - 作成した HTML ファイルへのリンク、埋め込んだインタラクティブ要素を簡潔に報告する。

## 実行上の注意（過剰検証の禁止）

- 本ドキュメントは設計・合意確認のための軽量な資料であるため、**ブラウザ自動操作ツール（Puppeteer, Playwright, control-in-app-browser 等）による表示確認やQAテストは実行しない**。
- HTMLファイルを書き出したら無駄な検証ループを回さず、即座に完了報告を行う。
